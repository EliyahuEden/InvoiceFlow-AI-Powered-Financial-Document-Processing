# InvoiceFlow full system audit

**Audit date:** 21 November 2026 · **Repository baseline:** main at `3cc1bc247230ab132d2365bea52c613e718f2427` · **Scope:** current Windows checkout, committed GitHub baseline, disposable local services, and offline synthetic evidence.

## 1. Executive Summary

InvoiceFlow is a credible, locally runnable portfolio project with an unusually coherent core: source-linked bilingual invoice extraction, deterministic AP reconciliation, a human exception queue, and advisory policy retrieval. Fresh checks exercised the application with synthetic data. Three deployment gates are financial decision integrity, production security configuration, and restart-safe processing.

The most important finding was reproduced without any provider call: an invoice line with a matching SKU and missing quantity, unit price, and line amount returned `matched` with no findings. Code review also identified stale approval-step reuse after changed evidence and a concurrent approval update without a row lock. Controlled benchmark success does not cover those failure modes.

The frontend redesign and rules-first extraction are in the committed baseline. The local working tree already contained AI provider/configuration changes and an uncommitted faithfulness check. Findings explicitly marked **local draft** apply only to that work. Fresh local backend tests covered the current tree, while the GitHub CI run covers the exact committed SHA. This report is the only audit deliverable in the repository.

**Evidence language:** Reproduced = directly observed on synthetic data. Verified through code = concrete behavior follows from the inspected source, with runtime scope stated. Verified through tests = exercised in a named passing suite. Documentation-only = claim or artifact inspected without a new run. Suspected = design risk awaiting validation. Not verified = no adequate test or evidence collected. Severity reflects potential operational impact. Confidence separately describes the strength of the evidence.

Extraction-only and RAG artifacts were inspected but not replayed in this audit. No paid provider was used.

## 16. Final Verdict

**What is genuinely impressive.** Offline reproducibility, deterministic factors kept separate from AI advice, bilingual OCR and retrieval, source-linked evidence, actual database-backed role and tenant controls, and an end-to-end human workflow make this stronger than a generic LLM wrapper. For a junior or applied AI interview, explain why rules run first, when model fallback is profitable, why an existing quote can still fail to support a claim, and how held-out data differ from demos. For backend/full-stack roles, walk through decimal scale, revision conflicts, DB-based leasing, RLS and the RTL evidence UI.

**What still needs work.** Evidence completeness and approval state are the most material gaps. Worker durability, grounding, upload isolation and safe hosted defaults come next. A senior engineer will ask for race and failure tests, defensible tenant boundaries, realistic Hebrew/scanned error slices and a rollout/restore plan. Screenshots and polished model dashboards carry less weight than a transparent failure case and reproducible evidence.

**Biggest hidden risks.** A plausible incomplete match can move toward approval, a decision can outlive the evidence that justified it, and a real citation can lend authority to an unsupported conclusion. These can all survive an otherwise green demo.

**Unnecessary scope.** Defer payment execution, full ERP integration, supplier portals, heavy platform infrastructure and extra agent frameworks until a concrete need changes the scope.

**Highest-value next step.** After approval to implement, lock down missing-evidence and concurrent/stale-approval invariants with synthetic Postgres regression tests first. They protect the product's central promise and are feasible without broad redesign.

**Recruiter-facing demo.** Yes for a reviewed synthetic local walkthrough or recording. Show one clean and one discrepant Hebrew invoice, actual source evidence, a human decision, the audit trail and the offline metric limitations. Patch and configure security gates before putting the demo on the public internet. Put a short demo script and exact reproducibility commands near the top of the README.

**Real business use.** No. Before calling the portfolio project complete, close the P0 correctness cases, reconcile evidence claims with reproducible artifacts, rerun the seeded workflow and document known limits. A pilot additionally requires secure deployment, worker/reviewer recovery checks and repeatable restore. Production needs measured capacity, documented operating controls and independent evidence on the target document population.
